  根据需求详情分析需求，并生成详细需求分析文档的工作流定义。
  Args:
      inputs: {
          requirement, # 需求对象（来自 get_requirement）：{name, text, source, file}
          可选：@file:分析引用文件路径
      }
---

## 目标

分析当前需求，将分析结果输出到文件 `.testbuddy/md/analysis.md`（UTF-8，Markdown）。

**需求名称**：${requirement.name}

**需求详情**
<req_analysis>

```
${requirement.text}
```

</req_analysis>

## 工作流（严格遵守）

### 阶段一：信息收集与整合

1. 以录入的需求文本为准；若用户提供了关联文档/附件（粘贴文本或本地文件），一并合并，形成完整需求信息。
2. 不尝试联网获取需求内容；信息不足时在文档中标注"待澄清"。

### 阶段二：需求分析

3. 参考需求分析框架进行结构化分析。
4. 识别需求中的不明确点（功能歧义、语义矛盾、信息缺失）。

### 阶段三：文档生成（必须执行）

5. **必须**将分析结果写入 `.testbuddy/md/analysis.md` 文件。
6. 文档格式严格遵循`分析格式`规范。
7. 确保所有章节完整，空内容的可选章节需删除。

## 分析框架

### 1. 需求理解与解构

- **原始需求保留**：完整记录原始需求内容
- **核心场景识别**：提取关键业务场景和用户故事
- **功能模块划分**：按功能领域组织需求
- **依赖关系分析**：识别模块间的依赖和约束

### 2. 多源信息整合

- **关联文档整合**：合并用户提供的参考文档内容（如有）
- **信息去重与归纳**：整合多源信息，避免重复

### 3. 结构化分析

- **功能需求分析**：
  - 功能点详细说明
  - 输入输出定义
  - 业务规则描述
  - 用户交互流程
- **非功能需求分析**：
  - 性能要求（响应时间、吞吐量等）
  - 安全性要求（权限、加密、审计等）
  - 可用性要求（易用性、可访问性等）
  - 兼容性要求（浏览器、设备、系统等）
- **业务规则分析**：
  - 业务约束条件
  - 数据验证规则
  - 异常处理规则
  - 边界条件定义

### 4. 问题识别与澄清

- **功能歧义识别**：标注需求中表述不清的功能点
- **语义矛盾检测**：发现需求中的逻辑冲突
- **信息缺失标注**：列出缺少的关键信息
- **答案组织**：基于需求文本和用户补充信息提供答案，无法回答的标注待澄清

### 5. 文档生成（强制执行）

- **标准格式输出**：严格按照分析格式生成文档
- **章节完整性检查**：确保必需章节完整，可选章节按实际情况保留或删除
- **文件写入**：**必须**将内容写入 `.testbuddy/md/analysis.md`
- **确认反馈**：输出文件保存路径确认信息

## 输出管理

✅ 直接将分析结果写入 `.testbuddy/md/analysis.md`
✅ 文件格式严格遵循`## 需求分析格式`
✅ 仅输出确认信息："需求分析已完成，文档已保存至 .testbuddy/md/analysis.md"
❌ 禁止跳过文件写入步骤
❌ 严格禁止在对话中重复输出需求分析内容
❌ 严禁重复显示已写入文件的内容

## 分析格式

```markdown
# 需求分析

## 1. 完整需求信息

### 1.1 原始需求

[原始需求内容 - 必需]

## 2. 补充信息来源

### 2.1 用户补充的参考内容

[用户粘贴的关联文档、补充说明等]
**注意**：如果没有补充内容，删除此小节

## 3. 需求分析

### 3.1 需求概述

- **需求目标**：[明确的需求目标]
- **适用范围**：[需求的适用范围和边界]
- **核心场景**：[关键业务场景描述]

### 3.2 功能模块划分

#### 模块1：[模块名称]

- **模块描述**：[模块功能说明]
- **核心功能点**：
  1. [功能点1]
  2. [功能点2]
- **依赖关系**：[与其他模块的依赖]

#### 模块2：[模块名称]

[同上结构]

### 3.3 功能需求分析

- **输入定义**：[输入参数、数据格式]
- **处理逻辑**：[业务处理流程]
- **输出定义**：[输出结果、数据格式]
- **业务规则**：[业务约束和规则]

### 3.4 非功能需求分析

- **性能要求**：[响应时间、并发量等]
- **安全要求**：[权限控制、数据加密等]
- **可用性要求**：[易用性、可访问性等]
- **兼容性要求**：[浏览器、设备、系统等]
  **注意**：如果需求中没有明确的非功能需求，可简化此小节

### 3.5 业务规则与约束

1. [业务规则1]
2. [业务规则2]
3. [数据验证规则]
4. [异常处理规则]

### 3.6 边界条件与异常场景

- **正常边界**：[正常业务的边界条件]
- **异常场景**：[可能的异常情况]
- **错误处理**：[错误处理策略]

## 4. 问题与澄清

### 4.1 功能歧义

1. **问题**：[需求中不明确的功能点]
   - **答案**：[基于需求的答案，或标注"待澄清"]

### 4.2 语义矛盾

1. **问题**：[需求中的逻辑冲突]
   - **答案**：[基于需求的答案，或标注"待澄清"]

### 4.3 信息缺失

1. **问题**：[缺少的关键信息]
   - **答案**：[基于需求的答案，或标注"待澄清"]

**注意**：如果没有需要澄清的问题，可简化为"暂无需要澄清的问题"

## 5. 需求要点总结

1. [核心要点1]
2. [核心要点2]
3. [核心要点3]
4. [关键约束条件]
5. [重要依赖关系]
```
